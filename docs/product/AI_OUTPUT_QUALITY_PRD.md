# AI 输出质量评分与覆盖分析 PRD

## 背景

当前平台已经具备需求输入、AI 生成、宽松解析、评审和导出能力，但用户在“生成完成”后仍需要靠人工判断结果是否可靠：

- 需求里的关键点是否都被覆盖。
- 生成出的用例是否有重复、空泛或不可执行项。
- 优先级是否失衡，高风险场景是否不足。
- 如果结果质量一般，下一轮 prompt 应该怎么改。

现阶段平台的主要使用重心仍在“生成”和“解析”，因此本期不扩展到评审工作流或记录中心，而是在生成结果页增加一层即时质量检查，帮助用户在进入评审前快速判断结果是否可用。

## 目标

1. 对 AI 生成结果增加可读的质量评分和问题摘要。
2. 基于输入需求文本给出覆盖分析，识别已覆盖与缺失需求点。
3. 基于规则检测重复、空泛、不可执行用例。
4. 给出风险等级与优先级分布，帮助用户判断结果结构是否合理。
5. 自动输出下一轮 prompt 或人工修订的改进建议。

## 非目标

- 本期不接入额外 LLM 做二次质量评审。
- 本期不修改数据库 schema，不持久化质量报告。
- 本期不改记录列表、记录详情、评审中心的数据结构和展示。
- 本期不做跨语言语义理解，只做中文为主的启发式规则分析。

## 用户故事

### 测试工程师

作为测试工程师，我希望生成后立刻知道哪些需求点还没被覆盖，这样我可以决定是直接进入评审，还是先补充 prompt 重新生成。

### 测试负责人

作为测试负责人，我希望能一眼看到重复项、不可执行项和优先级分布，这样我能更快判断这批用例是否值得继续细化。

### 平台管理员

作为平台管理员，我希望质量检查是纯规则层、无需新增外部依赖，这样功能可稳定落地，也便于后续在 CI 中补充契约测试。

## 功能范围

### 1. 质量评分

在生成结果页展示 0-100 的综合质量分，分值由以下维度组成：

- 需求覆盖率
- 重复率
- 空泛/不可执行问题数
- 优先级与风险分布是否失衡

评分用于排序和提示，不作为阻断条件。

### 2. 需求点覆盖分析

基于生成时提交的文本输入、需求描述和补充说明，提取需求点列表，并对每个需求点给出：

- 已覆盖
- 部分覆盖
- 未覆盖

页面需至少展示：

- 覆盖率百分比
- 已覆盖数量 / 总数量
- 缺失需求点列表

### 3. 重复 / 空泛 / 不可执行检测

对生成结果中的每条用例执行规则检测，至少覆盖：

- 重复用例：标题和步骤语义高度重合。
- 空泛用例：标题、步骤或预期结果过于笼统。
- 不可执行用例：缺少明确操作、缺少预期、只有口号式描述。

页面需显示问题数量，并能列出典型问题用例标题。

### 4. 风险等级与优先级分布

展示：

- `P0/P1/P2/P3` 分布
- `high/medium/low` 风险分布

风险等级本期由规则推断，不新增模型调用。高风险应优先覆盖登录、支付、权限、数据变更、核心主流程等场景。

### 5. 改进建议

根据覆盖、重复、可执行性和分布情况，生成 2-5 条短建议，例如：

- 补充未覆盖的退款失败场景。
- 将“验证功能正常”类标题细化为具体操作与结果。
- 为登录和权限链路补足高风险用例。

## 交互范围

本期只在“生成测试用例”页结果区域新增质量检查面板。

- 生成成功后自动展示。
- 重新生成前清空。
- 不影响原有导出、筛选、分页和分享操作。

## 验收标准

- 非流式和流式生成完成后，结果页都能看到质量检查面板。
- 面板至少包含：综合评分、覆盖率、问题摘要、优先级分布、风险分布、改进建议。
- 当存在未覆盖需求点时，页面能明确列出缺失项。
- 当存在重复/空泛/不可执行问题时，页面能列出问题类型和命中用例标题。
- 前后端测试覆盖核心规则计算和接口回传。
- 执行 `pnpm -C frontend test:unit`、`pnpm -C backend test`、`pnpm -C frontend build`、`pnpm -C backend build` 均通过。

## 风险与约束

- 中文需求点提取和覆盖匹配是启发式规则，不能保证语义级 100% 准确。
- 质量评分是辅助信号，不应替代人工评审。
- 由于本期不持久化质量报告，离开生成页后不会在其他页面复现同一份分析结果。
- 若输入文本极短或仅上传文件且解析文本为空，覆盖分析应优雅降级为“无法计算覆盖率”。
